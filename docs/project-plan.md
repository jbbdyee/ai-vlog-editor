# AI Vlog Editor - Project Plan

> 제품의 최신 장기 범위는 [`product-spec.md`](product-spec.md), 현재 구현 범위는 [`mvp-v1-spec.md`](mvp-v1-spec.md)를 기준으로 한다.

## 1. 프로젝트 한 줄 정의

사용자가 촬영 중 남긴 자연어 편집 의도와 이후 수정 요청을 바탕으로,
긴 원본 영상의 탐색부터 실제 편집까지 수행하는 개인화 AI 브이로그 편집 서비스.

---

## 2. 문제 정의

브이로그 촬영 자체보다 촬영 이후의 편집 과정에 많은 시간과 노력이 필요하다.

특히 몇 시간 분량의 원본에서 사용할 장면을 다시 찾고,
불필요한 부분을 제거하고, 자막을 작성하고,
사용자의 취향에 맞게 편집하는 과정이 반복적인 부담이 된다.

완전 자동 편집은 시간을 줄일 수 있지만,
AI가 사용자가 생각하는 재미있는 장면이나 중요한 순간까지
정확하게 판단하기 어렵다는 문제가 있다.

따라서 이 프로젝트는

> 사용자의 창작 판단은 남기고,
> 반복적인 탐색과 편집 노동은 AI에게 맡긴다.

를 핵심 원칙으로 한다.

---

## 3. 핵심 사용자 흐름

1. 사용자가 영상을 촬영한다.
2. 촬영 중 필요한 순간에 자연어 편집 메모를 남긴다.
   - "AI야 방금 장면 꼭 살려줘."
   - "이 부분은 짧게 써줘."
   - "여기부터는 빼도 돼."
3. 촬영한 원본 영상을 업로드한다.
4. AI가 음성을 STT로 변환하고 편집 지시를 탐지한다.
5. 편집 지시와 관련된 장면 후보를 찾는다.
6. 사용자가 후보 장면을 빠르게 확인한다.
7. AI가 편집 계획을 생성한다.
8. 실제 영상 초안을 생성한다.
9. 사용자는 자연어로 수정 요청을 한다.
10. AI가 수정 의도를 해석하고 실제 영상에 다시 반영한다.

---

## 4. 개발 접근 방식

기능을 구현하는 것만으로 성공 여부를 판단하지 않는다.

각 핵심 기술은 먼저 단순한 Baseline을 구현하고,
테스트 데이터에서 결과를 측정한 뒤 문제를 분석하여 개선한다.

### 기본 개발 흐름

Baseline 구현  
→ Evaluation  
→ Failure Analysis  
→ Improvement  
→ Baseline과 성능 비교

이를 통해 단순히 "동작하는 AI"가 아니라,
왜 실패했고 어떻게 개선했는지를 설명할 수 있는 시스템을 만든다.

## 5. MVP v1

첫 번째 목표는 전체 서비스를 완성하는 것이 아니다.

촬영 중 자연어 편집 메모를 이용하여
사용자가 의도한 장면을 찾아 실제 영상 파일로 추출하는
하나의 End-to-End 파이프라인을 구축한다.

### Input

짧은 테스트 영상

### Process

영상  
→ 오디오 추출  
→ STT  
→ 타임스탬프 생성  
→ 촬영 중 편집 메모 탐지  
→ 관련 장면 구간 추론  
→ FFmpeg 영상 자르기

### Output

사용자가 촬영 중

> "AI야 방금 장면 꼭 살려줘."

라고 말한 경우,

해당 편집 메모를 탐지하고
"방금 장면"이 의미하는 영상 구간을 찾아
실제 MP4 클립으로 출력한다.

---

## 6. MVP v1 Baseline

초기부터 복잡한 AI 추론을 적용하지 않는다.

먼저 단순한 규칙 기반 Baseline을 구축한다.

예:

편집 메모 발생 시점: 01:48

"방금 장면" Baseline:

→ 편집 메모 발생 이전 15초를 후보 장면으로 선택

이 결과를 기준으로 실제 사용자가 의도한 장면과 비교한다.

이후 다음 정보를 단계적으로 활용하여 장면 탐색 성능을 개선한다.

- STT 문맥
- 주변 대화
- 침묵 구간
- 장면 전환
- 영상 정보
- 자연어 편집 의도

### Baseline Window

초기 Baseline에서는 편집 메모 발생 이전 15초를
후보 장면으로 선택한다.

15초는 최적값으로 가정한 수치가 아니라
첫 비교 실험을 위한 임시 기준값이다.

이후 다음과 같은 고정 구간을 비교한다.

- 5초
- 10초
- 15초
- 30초

각 구간의 Ground Truth 대비 성능을 측정하고,
고정 시간 방식 자체의 한계를 분석한다.

---

## 7. MVP 성공 기준

단순히 MP4 파일이 생성되는 것을 성공으로 판단하지 않는다.

### Pipeline Success

영상 업로드부터 실제 MP4 장면 추출까지
전체 파이프라인이 정상적으로 실행되어야 한다.

### Edit Memo Detection

촬영 중 남긴 편집 메모가 STT 결과에서 탐지되어야 한다.

### Scene Retrieval

AI가 선택한 장면과 사용자가 실제로 의도한 장면을 비교한다.

초기 Baseline에서는 정답 장면과의 시간 차이와
선택된 영상 구간의 겹침 정도를 측정한다.

구간 단위 평가는 IoU(Intersection over Union)를 사용한다.

### 초기 목표 기준

MVP v1의 초기 평가 기준은 다음과 같이 설정한다.

- 편집 메모 탐지 성공률: 90% 이상
- 예측 장면과 Ground Truth의 IoU: 0.5 이상
- 편집 메모 탐지 후 실제 MP4 생성 성공률: 100%

위 수치는 초기 실험을 위한 가설적 기준이며,
테스트 데이터와 실제 사용 결과를 바탕으로 조정한다.

초기 소규모 평가셋의 결과를
일반적인 시스템 성능으로 해석하지 않는다.

---

## 8. Evaluation Strategy

AI의 성능을 검증하기 위한 테스트 영상 세트를 직접 구축한다.

각 테스트 영상에는 사람이 직접 정한
정답 구간(Ground Truth)을 기록한다.

예:

| Test | 촬영 환경 | 정답 장면 | 편집 메모 시점 | 기대 결과 |
| --- | --- | --- | --- | --- |
| 01 | 조용한 실내 | 00:20~00:28 | 00:31 | 해당 장면 탐색 |
| 02 | 실내 + 배경음 | 00:42~00:50 | 00:55 | 해당 장면 탐색 |
| 03 | 야외 | 01:10~01:25 | 01:28 | 해당 장면 탐색 |

### Evaluation Dataset v0.1

초기 Spike 단계에서는
5개의 짧은 테스트 영상을 사용한다.

목적은 통계적으로 일반화된 성능을 주장하는 것이 아니라,

- End-to-End 파이프라인이 동작하는지
- 평가 방법 자체가 유효한지
- 어떤 실패 유형이 발생하는지

를 확인하는 것이다.

평가 방식이 안정화된 이후
촬영 환경별 데이터를 추가하여 Evaluation Dataset을 확장한다.

### 평가 대상

- 편집 메모 STT 인식 여부
- 편집 메모 탐지 여부
- 정답 장면과 예측 장면의 시간 차이
- 정답 구간과 예측 구간의 IoU
- 전체 파이프라인 성공 여부

---

## 9. STT Robustness

브이로그는 일반적인 음성 녹음보다 STT 환경이 어렵다.

실제 촬영에서는 다음과 같은 상황이 발생할 수 있다.

- 야외 소음
- 바람 소리
- 배경 음악
- 여러 사람의 대화
- 작은 목소리
- 카메라와 사용자의 거리

따라서 STT 성능을 하나의 고정된 조건에서만 평가하지 않는다.

### 테스트 환경

평가셋이 확장되는 단계에서 다음 환경을 포함한다.

- Test A: 조용한 실내 + 1명
- Test B: 실내 + 배경음
- Test C: 야외 + 주변 소음
- Test D: 야외 + 바람
- Test E: 여러 사람의 대화

초기 MVP는 조용한 환경에서 먼저 동작시키고,
이후 환경별 편집 메모 인식 성능을 비교하며 개선한다.

## 10. 핵심 기술 문제

### 1. 자연어 편집 지시 탐지

일반적인 대화와

> "AI야 방금 거 살려줘."

같은 편집 지시를 구분해야 한다.

초기에는 명확한 트리거 표현을 사용하고,
이후 다양한 자연어 표현으로 확장한다.

### 2. 자연어 참조 해상도 (Reference Resolution)

"방금", "아까", "여기", "이 부분"과 같은 표현이
실제 영상의 어느 시간 구간을 의미하는지 판단해야 한다.

특히 "방금"은 항상 일정한 시간을 의미하지 않는다.

따라서 단순 시간 규칙을 Baseline으로 사용한 뒤,
문맥과 영상 정보를 이용하여 점진적으로 개선한다.

이 문제를 AI Vlog Editor의 핵심 기술 과제 중 하나로 정의한다.

### 3. STT 강건성

촬영 환경에 따라 편집 메모 자체가 잘못 인식될 수 있다.

STT 오류가 이후 장면 탐색 전체에 영향을 주기 때문에
환경별 인식 성능을 측정하고 실패 사례를 분석한다.

### 4. 자연어를 실제 편집 명령으로 변환

예:

> "카페 부분은 줄이고 야경은 길게 해줘."

라는 요청을 실제 영상 구간과 편집 작업으로 변환해야 한다.

### 5. AI 판단과 영상 처리 도구 연결

AI가 텍스트 답변만 생성하는 것이 아니라,
판단 결과가 FFmpeg 등의 실제 영상 처리 작업으로 이어져야 한다.

### 6. 사용자 편집 취향 학습

반복적인 수정 기록에서 편집 취향을 추출하고
다음 영상에 반영할 수 있어야 한다.

## 11. 기술 도입 전략

필요하지 않은 기술을 MVP 단계부터 도입하지 않는다.

각 기술은 실제 문제가 발생했을 때 도입한다.

### MVP v1

- Python
- FastAPI
- FFmpeg
- STT

목표:

영상  
→ 음성  
→ 텍스트  
→ 편집 메모  
→ 장면 구간  
→ 실제 MP4

파이프라인 구축

STT 엔진은 MVP 착수 전 후보를 비교한 뒤
정확도, 타임스탬프 지원, 실행 비용, 처리 속도,
개인정보 처리 방식을 기준으로 하나를 선택한다.

### v2+

필요에 따라 도입:

- LLM
- Embedding
- Semantic Search

목표:

자연어 장면 검색과
보다 정교한 장면 탐색

### Later Stage

실제 필요성이 확인된 경우 도입:

- PostgreSQL / Supabase
- Redis
- Tool Calling
- Agent Workflow

기술을 사용하기 위한 기능을 만들지 않고,
문제를 해결하기 위해 필요한 기술만 선택한다.

- 사용자 수정 이력 저장

- 여러 장면의 역할과 관계 분석

- 세로 화면 Auto Reframe과 자막 적용
- 플랫폼 출력 프로필에 따른 실제 영상 생성

### v7 - Agent Workflow Review

- 영상 분석
- 장면 탐색
- 편집 계획
- 편집 실행
- 결과 검증

일반 워크플로우로 해결하기 어려운 동적 재계획 사례가 확인된 경우에만
Agent 또는 Multi-Agent 구조를 검토한다.

## 13. Privacy & Data Handling

초기 MVP에서는 개인 테스트 영상을 사용하고
가능한 범위에서 로컬 처리를 우선한다.

초기 테스트 원본은 장기 보관하지 않는다.

향후 실제 사용자 영상을 처리하게 될 경우 다음을 별도로 설계한다.

- 원본 영상 저장 여부
- 데이터 보관 기간
- 원본 삭제 정책
- 사용자별 접근 제어
- 외부 AI API로 전달되는 데이터 범위
- 민감한 영상 및 음성 데이터 보호

개인정보 보호 설계가 완료되지 않은 상태에서는
불필요하게 사용자 원본 영상을 서버에 장기 저장하지 않는다.

---

## 14. 프로젝트 원칙

기능이나 기술을 추가하기 전에 다음을 확인한다.

1. 긴 영상의 편집 노동을 실제로 줄이는가?
2. 사용자의 편집 의도를 보존하는가?
3. AI가 필요한 이유가 명확한가?
4. 실제 영상 결과물에 영향을 주는가?
5. 구현 결과를 측정하거나 검증할 수 있는가?
6. Baseline보다 실제로 개선되었는가?
7. 지금 단계에서 정말 필요한 기술인가?

위 조건과 관계없는 기능은 우선순위를 낮춘다.

## 15. 변경 기록

### v0.1

- 프로젝트 문제 정의
- 핵심 사용자 흐름 정의
- MVP v1 범위 설정
- 단계별 기술 로드맵 작성

### v0.2 - Evaluation 중심 개발 전략 추가

#### 문제 발견

초기 계획은 End-to-End 파이프라인 구축에는 초점이 맞춰져 있었지만,
"관련 장면을 찾았다"는 성공 기준이 명확하지 않았다.

또한 실제 브이로그 환경에서 발생하는
STT 오류와 자연어 참조 해상도 문제에 대한
구체적인 검증 전략이 부족했다.

#### 변경한 방향

- 단순한 장면 탐색 Baseline부터 구현
- Ground Truth 기반 테스트 영상 구축
- STT 환경별 성능 평가
