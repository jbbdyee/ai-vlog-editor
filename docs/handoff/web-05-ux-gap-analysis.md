# WEB-05 — React 편집기 사용성·Streamlit 기능 공백 분석

상태: **코드·계약 분석 완료, 제품 기능 변경 및 신규 사용자 검증 미실행**. 점검일 2026-10-26, Windows `main` HEAD `1a2d7d71c4c2bbdc8d01a917227cd176d7fc7843`. 기존 WEB-01~04와 EVAL-01/02 미커밋 문서·코드, 백엔드 테스트 3개를 보존했다. 원본·GT·Manifest, 제품 코드·의존성·DB·출력 파일을 수정하지 않았고 외부 API를 호출하지 않았다. 실제 두 영상 Chrome E2E는 [WEB-04 기록](web-04-react-e2e-validation.md)의 과거 실행이며 WEB-05에서 다시 실행하지 않았다. GT는 여전히 미동결이고 [EVAL-01](eval-01-scene-candidate-quality.md) 정량 품질 평가도 미실행이다.

## 실제 구현 기준

- React는 `web/src/features/projects/home-page.tsx`, `project-page.tsx`, `web/src/features/scenes/scene-analysis.tsx`, `web/src/features/edit/edit-render.tsx`와 `web/src/api/`를 확인했다. 프로젝트 ID URL, 업로드 XHR, TanStack Query의 프로젝트별 키, 2초 활성 상태 폴링, 후보/계획/렌더/다운로드 UI가 있다. 영상 재생용 `<video>`·프레임·자막 미리보기 UI는 없다.
- Streamlit은 `frontend/app.py`와 `frontend/api_client.py`를 확인했다. 프로젝트 ID로 후보·진단·편집 계획·렌더를 다루며 수동 새로고침을 쓴다. 별도로 오래된 단일 영상 `/videos/process` 흐름에서 사용자가 5/10/15/30초 Window를 선택하고 Transcript·EditMemo·MP4 클립을 확인한다. **`st.video`는 이 레거시 클립에만** 사용된다. 프로젝트 최종 렌더나 원본·SceneCandidate 구간을 재생하는 UI는 아니다.
- FastAPI는 `backend/app/routers/projects.py`, `videos.py`, `backend/app/services/project_render_execution.py`, `backend/app/main.py`를 확인했다. 다음 표에서 `/projects`는 기존 로컬 개발 API를 뜻한다. 프로젝트/렌더 ID 연결과 경로 검증은 사용자 인증·소유권 검증이 아니다.

## 실제 사용자 질문에 대한 답

1. **후보 내용 확인/선택 전 재생:** 불가. 원본 파일명과 시각·Evidence 유형만 보며 장면의 실제 영상·오디오는 볼 수 없다. `SceneAnalysis` 카드의 파일명은 `processing.sources`와 소스 ID를 매칭해 표시한다. 계획의 **선택된 순서 목록은 시각과 후보 ID 중심**이라 여러 원본의 구분이 카드보다 어렵다(`edit-render.tsx`).
2. **순서 변경:** 가능. React 위/아래 버튼으로 이동하며 저장 전 변경을 표시한다. 다수 후보를 한 번에 재배치하거나 영상 내용을 보며 이동하는 타임라인은 없다. 현재 API 자체가 순서 있는 후보 ID 목록만 지원한다.
3. **렌더 전 예상 결과:** 볼 수 없다. 저장된 계획의 순서·구간 정보로만 예상하며, 음성·컷 연결·자막 결과는 렌더 뒤 파일을 내려받아 확인해야 한다.
4. **렌더 후 화면 재생:** React 프로젝트 화면과 Streamlit 프로젝트 화면 모두 불가. React는 MP4 바이트를 `Blob`으로 받아 다운로드 링크로 저장한다. Streamlit의 `st.video`는 프로젝트 렌더가 아닌 별도 레거시 클립이다.
5. **실패·복구:** 소스 처리/분석/렌더 상태와 오류 코드, 수동 재조회·일부 재시도 버튼은 있다. 새로고침하면 DB의 소스·후보·편집 계획은 다시 읽는다. 장면/렌더 실행 기록은 서버 프로세스 메모리에만 있고, 특히 완료 렌더의 다운로드 권한은 서버 재시작 후 복구되지 않는다. UI도 `NOT_STARTED`를 이전 성공으로 해석하지 않는다. 오류 코드만으로 사용자가 환경 문제를 스스로 해결하기 어려운 경우가 남는다.
6. **프로젝트 재개:** ID나 URL을 기억하면 React에서 프로젝트·소스·저장 계획·후보를 다시 열 수 있다. 전체 프로젝트 목록, 최근 프로젝트 복구, 이전 렌더 기록 목록은 없다. React 화면의 단계 막대는 고정된 문구여서 실제 완료 단계와 일대일로 갱신되지 않는다(`project-page.tsx`의 `Steps`).

## FastAPI 계약·보안 공백

| 항목 | 코드로 확인한 상태 | 후속 설계 방향(이번 작업에서 미구현) |
| --- | --- | --- |
| 원본 영상 스트리밍 | 프로젝트 소스 업로드·상태 API는 있으나 원본 조회/재생 API 없음. `SourceStorage.resolve()`는 내부 렌더 경로에서만 사용 | 프로젝트·소스 연결 검증, 저장소 기준 안전한 경로 확인, MIME/크기·파일 타입 확인, 필요한 범위 요청을 갖춘 로컬 전용 미디어 조회 계약 설계 |
| 후보 구간 미리보기 | 후보 API는 시간 범위만 제공. 별도 클립 미리보기 API 없음 | 원본 접근 계약과 정확한 원본 타임스탬프 매핑을 먼저 검증. 브라우저 seek로 충분한지 코덱·정확도 실험 후, 필요할 때만 안전한 임시 클립 API 검토. 기존 렌더 알고리즘을 미리보기로 복제하지 않음 |
| HTTP Range | 현재 설치된 Starlette `FileResponse` 소스에는 `Accept-Ranges: bytes`와 단일/복수 범위의 206 처리 코드가 있다. 기본/자막 MP4 다운로드 라우트는 `FileResponse` 사용 | **해당 프로젝트 라우트의 실제 206·416·seek 브라우저 동작은 WEB-05에서 실행 검증하지 않음.** 원본 미디어 라우트 신설 시 프록시·보안 검사 포함 별도 검증 |
| 렌더 결과 미리보기 | 기본 MP4 `inline` 다운로드 URL은 현 프로세스의 완료 기록이 있을 때만 응답. 자막 MP4는 `attachment`; SRT 조회는 없음 | 우선 기존 기본 MP4를 안전한 `<video>` 재생으로 연결할 수 있는지 별도 E2E로 검증. 자막 MP4는 독립 inline 조회 또는 제한된 재생 계약을 검토 |
| SRT 다운로드 | `final.srt`는 파일로 생성되나 `/projects`에는 SRT 조회/다운로드 라우트 없음 | 편집 전 판단에 필요한지 확인한 뒤 렌더 ID·경로 검증을 재사용하는 읽기 전용 계약 설계 |
| 프로젝트 목록 | `POST /projects`와 `GET /projects/{id}`만 존재 | 로컬 프로젝트 재진입 필요를 확인한 뒤 제한된 목록 API 또는 사용 브라우저의 명시적 최근 ID 저장 비교. 인증 전 외부 공개 금지 |
| 렌더 재시작 복구 | `ProjectRenderRunRegistry`의 상태·완료 ID가 메모리 dict에만 있다. 파일 잔존만으로 재조회·다운로드 불가 | 결과 메타데이터의 안전한 영속화·파일 검증·계획 버전 연결·재시작 불완전 상태 구분을 별도 백엔드 설계로 처리 |
| 보안/CORS | `backend/app/main.py`에 인증·소유권 검증과 CORS middleware 설정이 없다. Vite는 같은 origin의 `/api`를 로컬 FastAPI로 프록시 | UUID 연결·경로 검증을 인증으로 표현하지 않음. 원본/미리보기 API는 민감 미디어 노출이므로 인증·권한·로컬 전용 경계와 배포 정책을 함께 설계. 공개 배포는 계속 금지 |

기존 렌더 다운로드는 정규화된 render ID, 현재 프로세스의 Project/Render 연결, 허용된 출력 루트, 파일 존재·크기를 확인한다(`projects.py`의 `_completed_render_file`/`_completed_hard_subtitle_file`). 이는 경로 조작을 줄이는 검사지만 사용자별 권한을 제공하지 않는다. 특히 자막 파일의 별도 경로 조건과 기본 MP4 조건은 각기 구현돼 있으므로 새 재생 엔드포인트가 생기면 동등한 검증을 다시 적용해야 한다. React의 `fetchRenderFile()`은 파일 전체를 Blob으로 모아 큰 결과에서 메모리 부담이 있을 수 있으며 측정은 미실행이다.

## Streamlit 유지·제거 판단과 다음 구현 범위

React는 프로젝트 생성·업로드/소스 처리와 기존 프로젝트 장면 분석·후보/진단·편집 계획·렌더·두 MP4 다운로드를 연결했고 [WEB-04](web-04-react-e2e-validation.md)에서 두 실제 영상을 로컬 Chrome으로 통과했다. Streamlit에만 남은 것은 **레거시 단일 영상** fixed Window·Transcript/EditMemo 확인·생성 클립 재생/다운로드다. 두 화면 모두 프로젝트 원본·후보 구간·최종 영상의 재생을 제공하지 않는다.

**지금 Streamlit 제거는 보류한다.** 레거시 `/videos` 사용 목적을 유지할지 먼저 결정하고, React의 후보/결과 미리보기와 렌더 재시작 복구 범위를 구현·검증해야 한다. 제거 전에는 (1) 레거시 기능의 사용자 수요·보존 방법 결정, (2) React 기능별 계약·오류·두 MP4 다운로드 동등성, (3) 원본·후보·결과 재생의 실제 브라우저 검증, (4) 다중 소스·자막 실패·재시작·대용량·보안 회귀를 확인한다. Streamlit 실제 클릭 조작은 [TODO](../../TODO.md)에 여전히 미검증으로 기록되어 있으며 WEB-05에서 실행하지 않았다.

**다음 구현 단계 제안 — WEB-06:** 로컬 전용 미디어 조회 계약과 원본/후보 재생의 최소 범위를 먼저 설계·구현하고, 기존 후보 카드에 재생 제어를 연결한다. 다른 프로젝트 ID, 잘못된 경로, 없는 소스, 범위 요청/seek, 개인정보·권한 경계를 API 및 실제 Chrome으로 검증한다. 그 뒤 별도 단계에서 최종 MP4 재생·자막 검토와 렌더 영속 복구를 처리한다. 편집 계획·렌더 알고리즘, AI 추천 규칙, GT 계약은 그대로 둔다.
