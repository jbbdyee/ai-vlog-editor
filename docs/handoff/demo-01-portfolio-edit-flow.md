# DEMO-01 — 포트폴리오 편집 흐름 완성 (업로드 → AI 장면 추천 → 선택·자연어 요청 → MP4)

- 일자: 2026-11-03
- 우선순위: 포트폴리오 제출용 end-to-end 흐름. 기존 구현을 재사용했고, DB 스키마 변경은 없다.
- 상태 구분: 구현 완료, 합성 테스트 통과, **실제 영상 1개로 제한된 실제 검증**(격리 환경). 장면 추천 품질의 정량 평가(동결 GT)는 하지 않았다.

## 1. 막히던 지점

| 문제 | 원인 | 조치 |
| --- | --- | --- |
| 실제 MOV(춤 영상 246.5초)에서 후보가 0개라 이후 단계가 진행되지 않음 | 승격 규칙 3개가 모두 `AUDIO_ACTIVITY` 교집합을 요구한다. 이 영상은 오디오 활동이 상대 기준을 0.015 dB 차이로 넘지 못했다([기록](scene-preview-recovery-2026-11-03.md)) | 오디오 기반 교집합이 **하나도 없을 때만** 전사(말)×영상 움직임 교집합을 대안 규칙 `TRANSCRIPT_PLUS_VISUAL_ACTIVITY`로 사용 |
| 후보가 너무 짧거나 겹침 (0.1~3.2초, 평균 0.7~1.5초) | 원시 근거 교집합을 그대로 후보로 저장했다 | 승격 v0.4: 간격 1초 이하는 병합(병합 결과 최대 15초), 3초 미만은 앞뒤로 넓힘(원본 범위 안), 남은 겹침은 정리 |

- `build_promotion_manifest`(관측 근거 계약)는 바꾸지 않았다. 새 `build_scene_proposals`가 그 결과를 후처리한다.
- `PROMOTION_VERSION`을 v0.4로 올렸다. 장면 분석을 다시 실행하면 새 후보 집합이 활성화되고, 이전 후보는 DB에 남는다.
- 진단의 "지원 조합"에도 대안 규칙을 반영했다.

오프라인 비교(개발 DB에 캐시된 실제 근거를 읽기 전용으로 조회, 동일 입력):

| 영상 | v0.3 후보 | v0.4 후보 |
| --- | --- | --- |
| P1-S01 13.5초 | 5개, 0.18~2.14초 | 2개, 3.0~5.6초 |
| P1-S02 36.2초 | 12개, 0.1~3.2초, 겹침 1 | 6개, 3.0~5.1초, 겹침 0 |
| 춤 MOV 246.5초 | 0개 | 6개, 3.0~5.7초 |

기준값 3초·1초·15초는 편집 화면에서 볼 만한 장면 길이를 위한 제품 파라미터다. GT에 맞춰 조정한 값이 아니며, 평가 계약·GT·Manifest는 변경하지 않았다.

## 2. 추천 이유 UI

- **API:** `GET /projects/{id}/scene-candidates`의 후보에 `transcript_text`(장면 구간과 겹치는 STT 문장, 최대 160자)를 추가했다(선택 필드).
- **React:** 근거 유형을 한국어 이유로 표시한다.
  - 이유: 말하는 구간, 감탄·리액션 발화, 소리가 살아나는 구간, 화면 움직임
  - 주의: 긴 무음·정지 화면 포함
  - 실제 대사를 인용하고, 원시 코드는 툴팁으로 남긴다.
  - 장면 분석 목록과 편집 선택 목록 모두에 적용했다. 이유 표시는 근거 유형만 쓰므로 이전 서버에서도 동작한다.

## 3. 자연어 편집 요청 (최소 기능)

- **API:** `POST /projects/{id}/edit-suggestions {request}`. **읽기 전용**이며 아무것도 저장하지 않는다.
- **방식:** 규칙 기반 한국어 해석(`backend/app/services/edit_request.py`)이다. 외부 LLM은 쓰지 않는다(현재 실행 환경에는 키가 없다).
- **이해하는 조건:**
  - 목표 길이(초·분), 개수(`N개`)
  - 포함 단어(따옴표 구문 포함, 조사 제거), 제외 단어(`~빼고/제외/없이/말고`)
  - 성격(리액션·움직임·대화), 역순, 전부
- **동작:** 조건과 일치하는 장면을 점수순으로 골라 길이·개수 한도 안에서 담고, 시간순(또는 역순)으로 정렬한다. 장면별 이유와 메모(못 찾은 단어, 일치가 없으면 전체에서 선택)를 함께 돌려준다.
- **React:** "원하는 편집을 말로 요청하기" → "장면 제안 받기" → 제안 확인 → "제안을 선택 목록에 적용" → 기존 "편집 계획 저장" 순서다. 저장·렌더 계약은 그대로다. 이전 서버(404)에서는 "서버 업데이트 후 사용" 안내를 띄운다.

## 6. 남은 문제

1. **서비스 반영:** 실행 중인 8000은 이전 코드다. 새 후보 규칙·대사·자연어 요청 API를 쓰려면 QA-06 절차(migration `e3a1c9d27b45` → 8000 재시작)가 필요하고, 승인 대기 중이다. 이유 칩 등 React 변경은 5173에 이미 반영됐다. 자연어 요청은 현재 8000에서 "서버 업데이트 후 사용" 안내만 뜬다.
2. **기존 후보:** 기존 프로젝트의 후보는 장면 분석을 다시 실행해야 v0.4로 바뀐다. 이전 후보로 저장한 편집 계획은 무효 후보로 표시된다(기존 정책).
3. **오디오 기준 오분류:** 노래가 나오는 춤 영상인데 기존 오디오 분석기가 전체를 무음으로 판정해 "긴 무음 포함" 주의가 붙는다. 상대 기준 문제이고 이번에 바꾸지 않았다.
4. **자연어 해석의 한계:** 규칙 기반이라 동의어·문맥·영상 내용(무엇이 보이는지)은 이해하지 못한다. 키워드는 STT 대사에서만 찾는다.
5. **추천 품질:** 동결 GT로 평가하지 않았다. 검증은 실제 영상 1개(춤 MOV)뿐이며, 오프라인 비교 3종도 후보 수·길이만 본 것이다.
