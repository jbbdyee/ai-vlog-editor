# QA-02 — 렌더 결과 파일 무결성 설계와 격리 검증

상태: **설계·합성 파일 비용 측정·일회용 격리 DB DDL 시험 완료. 제품 코드·migration 파일·현재 개발 DB 변경 없음.** [QA-01 결함 재현](qa-01-render-recovery.md)의 expected failure는 그대로 유지한다.

## 현재 계약과 결함

- project_render_runs는 기본 MP4의 상대 경로·크기·길이·코덱, SRT/하드 자막 MP4의 상대 경로·크기, 실패 코드와 상태를 보관한다. 콘텐츠 해시는 없다. 완료 작업은 FFmpeg/FFprobe를 거친 결과를 받은 뒤 persistent_render_execution의 verified_output으로 고정 경로·루트·symlink·크기를 확인하고 COMPLETED를 DB에 기록한다. SRT/하드 자막 검증이 실패해도 기본 MP4의 완료는 유지한다.
- GET rendering·renders 목록과 기본/하드 자막 download는 같은 결과 참조를 사용한다. projects 라우터의 _completed_render_file 및 _completed_hard_subtitle_file은 경로·프로젝트/렌더 ID·symlink·존재·크기를 확인한다. React의 최종 영상 미리보기는 다운로드 URL을 video 요소에 넣으므로 Range 요청도 이 경로를 지난다. 현재 SRT 다운로드 API는 없다.
- QA-01은 동일 크기로 내용을 바꾼 기본 Mock MP4가 다운로드 HTTP 200과 download_available=true로 남는 현상을 재현했다. 다른 크기·파일 누락은 이미 차단한다. 기존 API의 콘텐츠 검사 부재는 FFprobe만 추가해도 모든 임의 바이트 변형을 증명할 수 없으므로 기록된 SHA-256과의 비교가 필요하다.

## 권장 정책

1. **완료 시 기록:** FFmpeg/FFprobe 성공과 기존 경로·크기 검증 후, 최종 이름으로 원자적 반영된 파일을 스트리밍 방식으로 SHA-256 계산한다. 기본 MP4는 해시가 없거나 계산/재검증에 실패하면 COMPLETED로 기록하지 않는다. SRT와 하드 자막 MP4는 실제로 생성·검증된 파일 각각의 해시를 기록한다. 선택 파일 실패는 기존과 같이 해당 파일의 오류로 남기고 기본 MP4의 성공을 보존한다. 해시 계산 뒤 DB 완료 commit 전에 파일이 바뀌는 경쟁은 출력 디렉터리의 불변 운영 규칙과 재검사로 줄이되 DB·파일의 완전한 원자성은 주장하지 않는다.
2. **조회·제공 시 검증:** GET rendering, 기록 목록, 기본/하드 자막 다운로드 및 video Range 요청에서 기존 경로·symlink·크기 검사를 먼저 수행하고, 기대 SHA-256이 있으면 전체 파일을 청크로 읽어 상수 시간 비교한다. 크기만 맞는 변형도 차단한다. 검증 결과를 크기·mtime만으로 장기 캐시하면 두 값을 보존한 변형을 놓치므로 엄격 모드에서는 요청별 해시를 생략하지 않는다. 여러 동시 요청에는 동일 파일의 진행 중 해시 작업을 공유하는 singleflight를 검토하되 서로 다른 시점의 요청까지 무조건 캐시하지 않는다. 파일을 메모리에 한꺼번에 적재하지 않는다.
3. **응답·상태:** 없는 파일은 기존 404와 RENDER_FILE_MISSING/MISSING을 유지한다. 해시 불일치는 409와 별도 안전 코드(예: RENDER_FILE_CORRUPT, SUBTITLED_RENDER_CORRUPT)로 구분한다. 기록의 원래 COMPLETED 상태·스냅샷·파일은 보존하고 현재 가용성만 false로 표시한다. React는 이를 재생/다운로드 불가로 안내한다. 기본 MP4가 불일치하면 현재의 기본 파일 선행 검증 계약에 맞춰 두 MP4 제공을 막는다. 하드 자막만 불일치하면 기본 MP4는 계속 제공한다. SRT만 불일치하면 기본 MP4 및 독립적으로 검증된 하드 자막 MP4는 유지하고 SRT 진단만 표시한다. SRT 제공 API는 이번 설계에서 추가하지 않는다.
4. **해시 없는 기존 완료 행:** NULL은 일치로 간주하지 않는다. 상태는 COMPLETED로 보존하되 integrity=UNVERIFIED, 제공은 기본적으로 차단하고 재검증 필요 코드를 표시한다. 과거 파일을 현재 존재한다는 이유만으로 자동 해시 등록하지 않는다. 신뢰할 수 있는 당시 백업/해시와 사람 승인에 따른 별도 감사 후 명시적으로 등록한다. 현재 개발 DB의 완료 기록은 QA-01 마지막 읽기 전용 확인에서 0건이었지만 다른 환경의 과거 기록은 별도 확인이 필요하다.
5. **복구:** 파일이 사라졌다가 원래 해시와 같은 바이트로 복원되면 다음 요청에서 다시 가용해질 수 있다. 서로 다른 내용으로 교체된 파일은 크기·코덱이 같아도 계속 차단한다. 기준 해시를 자동 갱신하지 않는다. 수동 재기준화가 필요하면 원본 기록과 새 파일을 보존하고 별도 승인·감사 기록을 요구한다.

FileResponse가 검증 후 파일을 여는 사이 외부 프로세스가 파일을 교체하는 TOCTOU는 SHA 검사만으로 완전히 해결되지 않는다. 출력 저장소의 쓰기 주체 제한·완료 후 불변성, 가능한 경우 검증한 파일 핸들에서 스트리밍하는 응답 설계를 구현 단계에서 함께 검토해야 한다. 현재 인증·소유권 부재 때문에 공개 배포 경계로 해석하면 안 된다.

## DB 변경 제안

revision b8c01e2a4f60의 후속 Alembic revision에서 project_render_runs에 base_sha256, srt_sha256, hard_sha256 세 nullable varchar(64)를 추가한다. 각 값은 NULL 또는 소문자 64자리 16진수만 허용하는 CHECK를 둔다. 기존 행은 NULL로 유지하며 자동 backfill하지 않는다. 새 COMPLETED 행에서 기본 MP4 해시 필수 조건은 migration의 전역 NOT NULL이 아니라 새 애플리케이션의 완료 전이 검증으로 적용한다. 역사적 행과 QUEUED/FAILED 행을 보존하기 위해서다. 필요하면 완료 상태+결과 경로+해시의 조건부 DB CHECK도 격리 데이터 분포를 확인한 뒤 도입한다.

배포 순서: 현재 DB 백업·격리 복원→기존 b8 revision 확인→후속 nullable migration 격리 upgrade→기존 행/NULL 보존 확인→새 코드의 생성/조회/다운로드 검증→기존 환경 적용은 별도 승인. 이전 코드가 새 컬럼을 무시할 수 있는지 확인하고 전환 중 새 렌더 접수를 통제한다. downgrade는 격리 DB에서 컬럼 삭제에 따른 **해시 증거 손실**을 확인하되, 실제 기록이 생긴 DB에서 무단 downgrade하지 않는다. 롤백은 우선 새 접수를 중지하고 DB·파일 백업을 유지한 채 이전 호환 코드로 복귀한다.

이번 QA-02에서는 **migration 파일을 만들지 않았다.** 일회용 격리 PostgreSQL에서 Alembic을 b8c01e2a4f60까지 올린 후, 제안한 세 nullable 컬럼과 정규식 CHECK SQL을 트랜잭션 안에서 시험해 세 컬럼 모두 nullable인 것을 확인하고 rollback했다. 첫 시도는 시험 스크립트의 SQLAlchemy autobegin 순서 오류로 DDL 전에 종료됐으며, 고친 재실행이 성공했다. 시험 DB는 제거했다. 이는 실제 후속 Alembic revision의 upgrade/downgrade 검증은 아니다.

## 비용·검증 계획

이 PC의 일회용 합성 파일에서 Python 스트리밍 SHA-256 3회 측정은 8MiB 약 0.003–0.008초, 64MiB 약 0.024–0.030초였다. OS 캐시가 영향을 주며 실제 대용량 MP4·저속 저장장치·동시 Range 요청의 지연을 예측하는 수치가 아니다. 엄격한 매 요청 해시는 파일 크기에 선형인 읽기 비용과 응답 전 대기 시간을 추가한다. 구현 전에 대표 크기 분포를 측정하고 100MiB/1GiB 등 합성 파일의 cold/warm·동시 1/4/16 요청, Range 탐색 연속 요청의 p50/p95·디스크 읽기량을 비교해야 한다. 무결성 검사를 끄는 빠른 경로를 기본값으로 두지 않는다.

특히 기록 목록이 20개이고 각 기본 MP4가 1GiB라면 목록의 가용성 계산만으로 최대 약 20GiB를 읽을 수 있다(자막 MP4 제외). 목록·현재 상태의 응답 지연이 허용치를 넘으면 응답 계약에 UNCHECKED 상태와 선택한 렌더 ID의 명시적 검증 경로를 추가하는 대안을 비교한다. 이 경우 미검증 항목을 download_available=true로 표시하지 않으며 React의 확인/재생 흐름도 함께 바뀐다. 크기·mtime 기반 영구 캐시만으로 엄격한 동일 크기 변형 검출을 주장하지 않는다.

| 같은 크기의 다른 바이트 | QA-01 expected failure를 그대로 실행해 다운로드와 미리보기 차단을 확인한 뒤에만 일반 통과 테스트로 전환 |

## 구현 전 승인·남은 결정

필수 승인 대상은 **후속 DB migration 및 기존 개발 DB 적용**이다. 해시 없는 완료 기록을 기본 차단하는 호환성 정책, 409 오류 코드/React 안내, 기본 MP4 손상 시 하드 자막 MP4도 차단하는 현행 종속 정책, 응답당 전체 해시 비용을 함께 확정해야 한다. 승인 전 QA-01 expected failure를 통과로 바꾸지 않고 제품 코드·DB·기존 렌더를 변경하지 않는다. 실제 영상 렌더, 현재 DB 쓰기, FastAPI/Vite/Tailscale 재시작, Git 커밋·Push는 이번에 수행하지 않았다.
