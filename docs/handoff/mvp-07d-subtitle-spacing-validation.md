# MVP-07D — SRT 자막 공백 복원 및 P1-S01 검증

검증 기준 커밋: `main` / `ad01fef10105229bac57f9917fbbc7e5ff6b44e5`, 2026-10-24. 원인은 [MVP-07B 분석](mvp-07b-root-cause-analysis.md)의 3절을 따른다. [MVP-07A 실제 영상 검증](mvp-07a-real-video-validation.md)의 당시 `아뭐야` 결과는 역사적 증거로 보존했다. 이번에는 제품의 `project_subtitles.py`와 별도 회귀 테스트만 수정했으며 STT·소스 저장, 렌더·다운로드 API, 원본 영상, 평가 계약·GT·Manifest는 변경하지 않았다.

## 원인과 변경

faster-whisper의 원래 단어 문자열은 `' 아'`, `' 뭐야'`처럼 앞 공백이 있으나 `stt_service._parse_word()`가 `.strip()`으로 제거한다. `source_processing._new_transcript()`는 그 단어와 공백이 남은 segment 문장 `아 뭐야`를 함께 저장한다. 기존 `map_subtitle_cues()`는 선택 단어를 구분자 없이 합쳐 `아뭐야`를 만들었다. 촬영자 기록 `어 뭐야`와 STT의 첫 음절 `아` 차이는 인식 문제이며 이번 변경 대상이 아니다.

자막 매핑에서 저장된 **segment 문장을 기준으로 단어 텍스트를 순서대로 정렬**하고, 선택된 인접 단어 사이에 원문에 실제 존재하는 공백·문장부호만 복원한다. 양끝의 문장부호도 해당 첫·끝 단어가 선택됐을 때 보존한다. 기존 DB에서 공백이 제거된 단어와 신규 STT 단어 모두 같은 경로를 사용한다. 선택되지 않았거나 시간이 유효하지 않은 단어의 텍스트는 복사하지 않는다. 그 사이에 관찰된 뒤쪽 공백만 사용할 수 있다. 원문에 단어 목록으로 설명할 수 없는 다른 글자가 있거나 단어와 segment가 맞지 않으면 기존 단어 결합으로 돌아가며, 한국어 단어마다 공백을 추정 삽입하지 않는다. 원본 전사와 단어 시각은 수정하지 않는다.

기존 반열린 시간 구간, 부분 겹침 단어 포함, 출력 클립 시각 비례 변환, 밀리초 반올림 정책은 그대로다. `_clean_text()`와 `format_srt()`의 개행 및 `-->` 삽입 방어를 유지하고, NUL·ESC 같은 ASCII 제어 문자도 공백으로 정리한다. 문장 원문이 단어열과 불일치하거나 원문 자체에 공백이 없으면 공백을 확정할 수 없다는 한계가 있다. 단어 일부만 선택 구간과 겹칠 때 단어 전체를 표시하는 정책은 별도 과제다.

## 테스트

Windows Python 3.12.15 / faster-whisper 1.2.1 / av 18.1.0 환경에서 관련 테스트를 실행했다. 새 `test_project_subtitle_spacing.py` 12건은 실제 faster-whisper 형태의 앞 공백 단어가 저장될 때의 동작, 기존 DB 형태의 공백 제거 단어, `아 뭐야`, 문장부호, 한국어·영어 혼합, 중복 토큰과 겹치는 시간, 누락된 단어 시간, 부분 겹침, 밀리초 반올림, 단어 기반 SRT 삽입 방어, NUL·ESC 제어 문자, 원문 불일치 시 보수적 처리 등을 확인한다. 기존 자막·STT·렌더·두 다운로드·하드 자막 테스트를 FFmpeg와 Docker를 사용 가능한 경로로 설정해 함께 실행한 결과 **78건 중 77건 통과, 실패 0, 건너뜀 1**이었다. 건너뛴 것은 Windows symlink 권한이 필요한 기존 렌더 API 테스트이며 통과로 집계하지 않았다. 합성 하드 자막 렌더 테스트는 실제 실행해 통과했다.

## P1-S01 실제 저장 데이터 재검증

07A의 실제 소스에 저장된 Transcript를 DB에서 읽었다. 첫 segment는 4.64~6.12초 `아 뭐야`, 저장 단어는 `아`(4.64~5.74초), `뭐야`(5.74~6.12초)다. 07A 검증자가 선택한 5.54~6.12초 후보와 당시 측정된 자막 출력 길이 0.566초로 다시 매핑한 새 SRT는 다음과 같다.

```srt
1
00:00:00,000 --> 00:00:00,566
아 뭐야
```

새 파일은 Git 무시 경로 `evaluation/tmp/mvp-07d-p1-subtitle-92cd914e6cad4f0ea0f7983a0e5fe615/`에 분리했다. 07A의 `final.mp4`를 읽기 전용 입력으로 복사하고 새 `final.srt`와 `final-subtitled.mp4`를 생성했다. 기존 세 렌더 파일의 실행 전후 SHA-256이 각각 동일함을 확인했다. 새 SRT SHA-256은 `f11d267141d2b66c42a3e9d9db55672b3b0535e0f5d1cf43326aee2719ed2d1c`, 새 하드 자막 MP4는 `0779164df658e4526c12d45e3044e90bf4c099ae0d3d0d702aa4ab1fe35fc700`이다.

FFprobe에서 새 기본 MP4와 하드 자막 MP4가 모두 **0.583333초**, H.264 영상 1280×720과 AAC 오디오를 포함함을 확인했다. 하드 자막은 해시가 확인된 한국어 글꼴과 네트워크를 차단한 Docker/libass 경로로 적용했다. 0.3초 프레임을 각각 추출해 기본 영상에는 글자가 없고 자막 영상에는 `아 뭐야`가 한글과 공백으로 표시됨을 육안 확인했다. 이 검증은 실제 영상에서 파생된 기존 짧은 MP4와 저장 전사를 재사용했다. 전체 실제 영상 STT·장면 추천·렌더를 다시 실행하거나 새로운 다운로드 API 요청을 수행한 결과는 아니다. API 계약은 기존 정상·오류 회귀 테스트로 확인했다. Streamlit 실제 클릭 조작과 전체 프레임·추천 정량 품질은 미검증이다.

## 영향과 남은 문제

SRT와 이를 이용한 하드 자막의 텍스트만 달라진다. 기본 MP4 생성·기존 렌더 결과·다운로드 파일명/MIME 계약·DB schema·STT 인식 내용은 변경하지 않았다. 기존 렌더 파일은 자동으로 갱신되지 않으며 향후 새 렌더부터 수정된 자막이 적용된다. segment와 단어의 표기가 불일치할 때의 공백, 선택 구간 경계에서 부분 단어의 처리, STT 첫 음절 오인식, 사용자 UI 조작, 다른 실제 영상 사례는 후속 검증·개선 범위다.
