# Cutory 공통 개발 규칙 (Codex·Claude)

사용자가 창작 판단을 내리고 시스템은 반복 노동을 줄인다. 구현은 `Baseline → Evaluation → Failure Analysis → Improvement` 순서로 진행한다. 새 기술이나 범위 확장은 Baseline 실패와 검증 근거가 있을 때만 결정한다. v1 완료 기록은 보존하고, v2 전체 완료·동결 GT 품질 합격·미래 v3 기능을 앞당겨 주장하지 않는다.

## 문서의 역할

- [SPEC](SPEC.md): 현재 서비스 요구·지원 범위·구조. 장기 제품 목표의 원본은 [Full Product Plan](../docs/product/full-development-plan.md), 버전 범위와 완료 기준의 원본은 [v2 Plan](../docs/roadmap/v2-plan.md)이다. 이 문서가 평가 계약을 대체하지 않는다.
- [IMP-PLAN](IMP-PLAN.md): 가까운 구현 순서와 진입·완료 조건. [TODO](TODO.md): 현재 상태와 차단 사항. [HANDOFF](HANDOFF.md): 환경·검증·인수인계.
- 기존 [루트 TODO](../TODO.md), [README](../README.md), [과거 handoff](../docs/handoff/), [평가 자료](../evaluation/)는 삭제하거나 새 문서에 복사해 덮어쓰지 않는다. 충돌하면 코드·현재 실행 결과를 먼저 확인하고 원본 문서와 차이를 기록한다.

## 변경과 검증

1. 기능·요구사항·설계가 바뀌면 해당 Source of Truth와 SPEC·IMP-PLAN의 관련 부분을 같은 작업에서 갱신한다. 구현·검증 상태가 바뀌면 TODO·HANDOFF와 필요한 README 요약도 갱신한다.
2. 오류 수정은 증상, 재현 조건, 원인, 변경, 회귀 테스트, 한계를 `docs/handoff/`의 단계별 기록에 남긴다. 긴 문제 해결 이력은 그곳에 두고 HANDOFF에는 최신 결론과 링크만 둔다.
3. **구현 완료**, 자동 테스트 통과, Mock 브라우저 검증, 실제 브라우저·API 검증, 실제 영상 검증, 동결 GT 정량 평가는 서로 다른 증거다. 실패·건너뜀·미실행을 통과로 세지 않는다.
4. LLM·VLM 출력은 관측·제안으로 취급한다. 사용자의 선택·저장이 최종 편집 계획을 결정한다. 결정적 규칙, 원시 Evidence, 모델 추론을 섞어 품질 합격처럼 설명하지 않는다.
5. 원본 영상·프레임·음성·개인정보·비밀키·민감한 로그를 Git에 추가하지 않는다. 평가 계약·GT·Manifest를 결과에 맞춰 변경하지 않는다.
6. 기존 미커밋 파일·DB·렌더 결과는 보존한다. DB 마이그레이션, 서비스 재시작, 커밋·Push, 유료 API 호출은 해당 작업의 사용자 승인 범위를 따른다.

## 현재 작업 경계

현재 코드에는 React·FastAPI·PostgreSQL·FFmpeg, 로컬 Ollama 기반 LLM 편집 제안과 VLM 화면 분석 경로가 있다. Redis는 현재 요청 처리에 사용 중이라는 근거가 확인되지 않았다. 실행 중인 8000에는 P0 추천 이유·무음 표시 백엔드 수정이 반영됐다. Docker 하드 자막 생성은 격리 합성 영상으로 검증했으며 실사 신규 렌더의 전체 품질은 미검증이다. 11월 14일 포트폴리오 제출 전에는 결함 수정·안전한 시연 검증에 집중하고 불필요한 기능 확장은 보류한다.
